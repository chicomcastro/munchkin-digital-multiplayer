# ADR-0010: i18n com 3 idiomas via dictionaries

- **Status**: Accepted
- **Data**: 2026-05-17

## Contexto

PT-BR foi a primeira língua. App é mobile-first, alvo Brasil. Mas:
- Spec original era em PT/EN mistura
- Distribuição internacional é trivialmente cara se não preparar agora
- Strings já estão centralizadas em `i18n.ts`

## Decisão

Estrutura `client/src/i18n/`:

```
i18n/
  index.tsx        Provider + hook useT() + setLocale
  pt-BR.ts         export const t: Translations
  en.ts
  es.ts
  types.ts         shape `Translations` (gigante)
```

`t` é exportado do `index.tsx` direto pra mantermos compat com o código existente: `import { t } from '../i18n'`. Cada vez que `setLocale` muda, o `t` exportado é reassignado e o React Context publica a mudança.

Detecção:
1. `localStorage['munchkin:locale']` (override do usuário)
2. `navigator.language` (`pt-BR` → pt-BR, qualquer outro `pt-*` → pt-BR, `es-*` → es, resto → en)
3. Fallback: `en`

Seletor: dropdown 🌐 no header do App, ao lado de 🔊/❓.

## Consequências

- ✅ EN/ES disponíveis sem refactor de componentes
- ✅ Adicionar idioma = criar 1 arquivo + adicionar ao registry
- ❌ Mudança de locale força re-render (via Context). Aceitável — não é hot path.
- ❌ Strings hardcoded em testes ainda usam PT-BR — testes não trocam locale. OK.
- ⚠️ Algumas strings têm gênero (você morreu vs you died vs has muerto) — cada locale traduz à sua maneira.

## Pontos de revisão

- Pluralização avançada: i18n libs (i18next, FormatJS) seriam justificadas. Por enquanto temos só `selling(n)` que faz singular/plural inline.
- Server-side strings (`Munchkin server listening on...`) ficam em EN — não são user-facing.
